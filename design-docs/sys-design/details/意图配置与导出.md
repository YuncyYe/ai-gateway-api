# 意图配置与导出

## 1. 概述

AI 意图配置（`intent_config`）是 AI 网关语义路由意图能力（AI intent）的控制面配置入口。数据面由 BFE `mod_ai_intent` 模块消费数据文件（`conf/mod_ai_intent/intent_questions.data`：问题集 + 全局置信度门控阈值）：模块按问题集调用决策服务对请求做意图分类，路由规则经条件原语 `req_ai_intent_in(...)` 按"问题名 + 选项名 + 置信门槛"命中目标集群。

BFE 侧 `mod_ai_intent` 已实现（提交 `7e482d90`，分支 `v1.8.9-dev`），本方案补齐控制面：维护意图配置（OpenAPI 全量读写）、持久化（单行覆盖式存储）、版本化下发（InnerAPI 导出 → conf-agent 落盘 → BFE 热更），与既有配置导出链路（`topic + generator + MD5 签名 + config_versions + Inner API 轮询`）一致，导出框架零改动。

路由规则消费方式**不变**：意图条件由调用方在 cond 字符串中直接书写 `req_ai_intent_in(...)`，控制面仅做语法编译校验（随 bfe 依赖升级生效），不做引用完整性校验。

## 2. 资源模型

### 2.1 单例资源 `intent_config`

- Open API 仅暴露单例级读写：`GET /open-api/v1/intent-config`（查询当前生效配置）+ `PUT /open-api/v1/intent-config`（全量覆盖式更新），照 `global-route-rules` 的全局资源先例；
- **全局单例**：全部 BFE 实例共享同一份意图配置（BFE 侧 `intent_questions.data` 是模块级单文件）；非租户/产品级资源；
- **单行覆盖式存储、不保存历史版本**：无 `/{id}` 端点、无 `enabled` 列、无版本表；PUT 覆盖唯一一行（固定 `id=1` upsert），回滚 = 重新 PUT 旧内容（从操作日志/人工备份找回）；
- **`version` 是下发链路内部字段**（`yyyyMMddHHmmss`）：PUT 成功即由服务端内部生成新版本（冲突时 +1s 顺延），**不在 OpenAPI 暴露**；每次 PUT 必然生成新 version（内容未变也不跳过），每次 PUT 必然触发一次下发；
- **空 `questions` = 停用意图分类的软开关**：`questions: []` 表示 BFE 侧所有问题的答案恒为 unknown、`req_ai_intent_in(...)` 永不命中，流量回落默认路由；恢复 = 发布非空配置，路由规则无需改动；
- 与 BFE 的对应：唯一一行 ⇔ 一份 `intent_questions.data`；BFE 侧数据文件名 `intent_questions.data` 已随 `7e482d90` 发布且 `QuestionsPath` 可配，文件名与资源名 `intent-config` 的差异为有意保留。

### 2.2 与 ai_cache_rules 集合资源的差异

| 维度 | ai_cache_rules（集合资源） | intent_config（单例资源） |
|------|---------------------------|---------------------------|
| 资源形态 | 全局有序规则集合（first-match-wins） | 全局单例（整份配置覆盖） |
| 写入语义 | 单事务 delete-all + insert-all 整体重建 | 单行覆盖 upsert（不存在插入、存在覆盖，固定 `id=1`） |
| 历史版本 | 不保存（同左，无版本表） | 不保存（同左，回滚 = 重新 PUT 旧内容） |
| 空集合语义 | `{"rules": []}` 清空全部规则 | `{"questions": []}` 停用意图分类（软开关） |
| API 形态 | 集合级 GET/PUT（无 `/{id}`） | 单例级 GET/PUT（无 `/{id}`） |
| 导出 Data 形态 | `Version` 外置 + `Config` 包装（`Config[product]` 两段结构） | **Data = 文件内容原样**（`Version` 内嵌文件，同 ai-route 端点形态） |
| topic | `mod_ai_cache` | `intent_config` |
| 静态 conf | Redis 连接不下发（`CopyFiles`） | `mod_ai_intent.conf`（决策服务地址/超时/缓存/熔断）不下发（`CopyFiles`） |

## 3. 数据模型

### 3.1 表结构

```sql
CREATE TABLE `intent_config` (
  `id` bigint NOT NULL AUTO_INCREMENT COMMENT '主键ID（固定 id=1，单行覆盖式存储）',
  `version` varchar(32) NOT NULL COMMENT '当前配置版本，时间戳格式 yyyyMMddHHmmss，每次 PUT 更新',
  `min_confidence` decimal(4,3) NOT NULL DEFAULT 0.600 COMMENT '全局置信度门控阈值 [0,1]',
  `questions` text NOT NULL COMMENT '问题集 JSON（可为 []，表示停用意图分类），结构同 BFE intent_questions.data 的 Questions[]',
  `created_at` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `updated_at` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  PRIMARY KEY (`id`)
) COMMENT='AI 意图配置（mod_ai_intent intent_questions.data 数据源：问题集+门控阈值，单行覆盖式存储）';
```

要点：

- **无 `enabled` 列、无版本表**：单行覆盖式全量读写模型下均冗余（见 §2.1）；
- `version` 仅作下发链路的变更检测依据，**不在 OpenAPI 暴露**（见 §2.1）；
- `questions` 以 JSON 文本**透传存储**（见 §3.2）；
- SQLite 版本（`db_ddl_sqlite.sql`）照 `ai_cache_rules` 的 SQLite 惯例改写：类型映射（`bigint`→`INTEGER`、`varchar`/`text`→`TEXT`、`datetime`→`TEXT`）+ `updated_at` 由触发器维护；新表对存量库为零迁移。

### 3.2 Open API 数据形态与 Questions JSON 透传策略

```json
{
  "min_confidence": 0.6,
  "questions": [
    {
      "name": "task_type",
      "type": "choice",
      "instructions": "这条请求属于哪类研发任务？",
      "criteria": {
        "coding": "编写或修改代码、调试、重构、代码审查",
        "test_writing": "编写测试用例、单元测试、集成测试、补充断言",
        "doc_writing": "编写文档、README、注释、接口说明、使用示例"
      }
    },
    {
      "name": "complexity",
      "type": "score",
      "instructions": "这个任务的复杂度如何？",
      "min_confidence": 0.7,
      "levels": [
        {"name": "simple", "description": "单步即可完成"},
        {"name": "medium", "description": "多步但模式常见"},
        {"name": "complex", "description": "需要深入推理或跨模块设计"}
      ]
    }
  ]
}
```

| 字段 | 类型 | 说明 | 合法性条件 |
|------|------|------|------------|
| `min_confidence` | number | 全局置信度门控阈值：决策服务答案置信度低于该值时视为 unknown（路由意图条件不命中） | 非必填；默认 `0.6`；`[0,1]` |
| `questions` | array | 问题数组（元素见下表）。**空数组 `[]` = 停用意图分类**（所有意图条件不命中，流量走默认路由），作为故障软开关 | 必填；0–10 个元素 |
| `questions[].name` | string | 问题名，路由 cond 中 `req_ai_intent_in("<name>", ...)` 按它引用 | 必填；非空；全部问题中唯一 |
| `questions[].type` | string | 问题类型 | `choice`（多选一）/ `score`（刻度打分）；必填 |
| `questions[].instructions` | string | 判定指令，发送给决策模型 | 必填；非空 |
| `questions[].criteria` | map<string,string> | 选项集合（type=`choice` 时必填）：选项名 → 选项描述 | 1–10 项；选项名唯一、非空、不含 `\|`；与 `levels` 互斥 |
| `questions[].levels` | array | 档位集合（type=`score` 时必填），从低到高 | 1–10 档；`name` 唯一、非空；与 `criteria` 互斥 |
| `questions[].min_confidence` | number | 该问题的门控阈值，覆盖全局 `min_confidence` | 非必填；`[0,1]` |

响应只读字段（仅 GET/PUT 响应携带，提交时忽略）：`created_at` / `updated_at`（RFC3339）。`version` 与 `id` 均为内部字段，不出现在 API 请求与响应中。

**Questions JSON 透传策略**：`questions` 在控制面**以 JSON 文本透传**，不在 ai-gateway-api 定义展开结构体（持久化层 `Questions` 为 JSON 字符串字段）。理由：**契约冻结源在 BFE**——`intent_questions.data` 的 JSON 结构与字段名以 `bfe/conf/mod_ai_intent/intent_questions.data` 及 BFE 侧文档为准；控制面只做**整体性校验**（JSON 合法、顶层字段齐全、逐问题字段合法、选项名不含 `|`），与 BFE `questions_conf.go` 的校验保持同口径，不重复定义一份可能漂移的结构契约。

## 4. Open API 读写语义

### 4.1 接口

| Method | Path | 权限 | 说明 |
|--------|------|------|------|
| GET | `/open-api/v1/intent-config` | `FeatureAIIntent + ActionRead` | 查询当前生效配置；未发布过返回 404；已发布但 `questions: []` 时正常返回空数组 |
| PUT | `/open-api/v1/intent-config` | `FeatureAIIntent + ActionUpdate` | 全量覆盖式更新（整体验证通过后生成新内部版本并置为生效）；返回更新后配置 |

### 4.2 校验（`model/iintent_config` 内整体校验，不经 `lib/validate`，任一失败整个 PUT 400，配置不变）

| 校验项 | 规则 |
|--------|------|
| `questions` | 必填数组；**0–10 个**元素（空数组 = 停用意图分类软开关，合法） |
| 每条 `name` | 非空、全部问题中唯一 |
| 每条 `type` | ∈ `choice` / `score` |
| 每条 `instructions` | 非空 |
| `type=choice` 的 `criteria` | 必填（与 `levels` 互斥）；1–10 项；选项名唯一、非空、不含 `\|` |
| `type=score` 的 `levels` | 必填（与 `criteria` 互斥）；1–10 档；`name` 唯一、非空、从低到高有序 |
| 全局/逐问题 `min_confidence` | ∈ `[0,1]` |

控制面校验把错误拦在写入前（fail-fast，400 `INVALID_ARGUMENT`）；BFE 侧校验（最后防线）：同口径校验项（BFE 协议上限 255，控制面更严不影响兼容；放宽时改控制面校验常量即可，无需动 BFE），热更时校验失败拒绝加载。

### 4.3 单行覆盖写入

PUT 的执行语义为**单行覆盖式 upsert**：

1. 意图配置整体校验（§4.2 口径）；
2. 生成新版本（`yyyyMMddHHmmss`，冲突时 +1s 顺延）；
3. `itxn.TxnStorager.AtomExecute` 开启事务（禁止 ad-hoc 事务）：不存在则插入（固定 `id=1`）、存在则覆盖唯一一行；失败整体回滚，配置保持原状；
4. 事务成功后记录操作日志（`resource_type=intent_config`，`before` 快照取自库中现状、`after` 为新配置）；校验失败同样记录一条失败审计；
5. 返回结果（version 不在响应暴露）。

本接口为该单例的唯一写入口，配置生效时延 = conf-agent 轮询周期（`ReloadIntervalMs`）+ BFE 热加载时间。

## 5. 导出契约（冻结）

> 本节是控制面/数据面的**接口契约**，以 BFE `mod_ai_intent` 的数据文件契约为冻结源（`bfe/conf/mod_ai_intent/intent_questions.data` 及 BFE 侧配置文档）。任何一侧改字段必须先改本节并知会另一侧。

### 5.1 文件结构

conf-agent 落盘文件：`conf/mod_ai_intent/intent_questions.data`（JSON，文件名为 BFE 侧既有契约，不随资源改名）：

```json
{
  "Version": "20260926120000",
  "MinConfidence": 0.6,
  "Questions": [
    {
      "Name": "task_type",
      "Type": "choice",
      "Instructions": "这条请求属于哪类研发任务？",
      "Criteria": {
        "coding": "编写或修改代码、调试、重构、代码审查",
        "test_writing": "编写测试用例、单元测试、集成测试、补充断言",
        "doc_writing": "编写文档、README、注释、接口说明、使用示例"
      }
    },
    {
      "Name": "complexity",
      "Type": "score",
      "Instructions": "这个任务的复杂度如何？",
      "MinConfidence": 0.7,
      "Levels": [
        {"Name": "simple",  "Description": "单步即可完成"},
        {"Name": "medium",  "Description": "多步但模式常见"},
        {"Name": "complex", "Description": "需要深入推理或跨模块设计"}
      ]
    }
  ]
}
```

- 导出字段为 BFE 文件契约的 PascalCase（`Version` / `MinConfidence` / `Questions` 及子字段 `Name` / `Type` / `Instructions` / `Criteria` / `Levels` / `Description`），转换发生在导出 Generator；Open API 为小写下划线词汇；
- **响应 `Data` = 文件内容原样**（Version 内嵌文件，同 `ai-route` 端点形态），**非 ai-cache 的 `Version` + `Config` 包装形态**——差异原因：ai-route / mod-ai-intent 的 BFE 加载器直接消费"版本内嵌于数据文件"的单段结构（落盘即加载），而 ai_cache 的文件契约是 `Version` 外置 + 按 product 分段的 `Config` 包装；控制面导出形态与各自 BFE 加载器逐字段对齐，不另造包装；
- 导出即落盘内容本身（`Version` / `MinConfidence` / `Questions`），无裁剪、无富化；问题数组顺序无优先级语义（一次分类调用并行评估全部问题），导出保持控制面提交顺序。

### 5.2 字段说明（tag 为 BFE `mod_ai_intent` 数据文件契约）

| 字段 | 类型 | 说明 | BFE 侧校验（最后防线） |
|------|------|------|------------------------|
| `Version` | string | 配置版本号（时间戳格式 `20060102150405`），内容任何变更必须更新 | 非空 |
| `MinConfidence` | number | 全局置信度门控阈值，低于该置信度的答案视为 unknown（路由意图条件不命中） | `[0,1]` |
| `Questions[].Name` | string | 问题名，路由 cond `req_ai_intent_in("<Name>", ...)` 按它引用 | 非空、唯一 |
| `Questions[].Type` | string | `choice` 多选一 / `score` 刻度打分 | 枚举校验 |
| `Questions[].Instructions` | string | 判定指令，发送给决策模型 | 非空 |
| `Questions[].Criteria` | map<string,string> | 选项集合（Type=`choice` 时必填，与 Levels 互斥）：选项名 → 描述 | 1–255 项（控制面收紧 1–10）；选项名唯一、不含 `\|` |
| `Questions[].Levels` | array | 档位集合（Type=`score` 时必填，从低到高，与 Criteria 互斥） | 1–255 档（控制面收紧 1–10）；Name 唯一 |
| `Questions[].MinConfidence` | number | 逐问题门控阈值，覆盖全局 `MinConfidence` | `[0,1]`；缺省用全局 |

要点（出自 BFE 侧文档，控制面透传不另做解释）：

- `Type` 仅 `choice|score`；choice 带 `Criteria`、score 带 `Levels`，互斥且必填其一；
- `Type=score` 时 BFE 将决策服务返回的期望档位索引映射回档位名后供路由条件匹配（路由规则侧始终面对离散名）；
- 门控语义：答案置信度低于生效阈值 → 该问题读取时视为 unknown（读取时计算，阈值热更即时生效）。

## 6. 生成器流程

### 6.1 入口

```go
func (m *IntentConfigManager) ConfigExport(ctx context.Context, lastVersion string) (*iversion_control.ExportData, error)
```

### 6.2 `IntentConfigGenerator` 流程

1. `Fetch` 取当前行；无记录 → 返回 nil（不导出，BFE 维持现状）；
2. 组装 `IntentConfigDataExport{Version, MinConfidence, Questions(RawMessage)}`——Data 即 `intent_questions.data` 文件内容原样（§5.1）；
3. 套 `iversion_control.ExportConfig(ctx, ConfigTopicIntentConfig, generator)` 标准流程：生成数据 → MD5 签名 → 比对 `config_versions`（`name="intent_config"`）→ 导出内容 version 与上次导出相同返回 nil（不触发 conf-agent 落盘与 BFE 热更）→ 不同则插新版本（版本号 = 时间戳 `20060102150405`，同 Topic 严格单调递增，机制见《InnerAPI配置导出与版本控制.md》）。

topic 常量 `ConfigTopicIntentConfig = "intent_config"` 定义在 `model/iintent_config/` 包内（与 ai_cache 的 topic 定义在自身包内一致）。

### 6.3 Inner API 端点

```go
// endpoints/innerapi_v1/intent_config_export/export.go（或并入既有 export 组织）
var ExportRoute = &xreq.Endpoint{
    Path:       "/configs/mod-ai-intent",
    Method:     http.MethodGet,
    Handler:    xreq.Convert(ExportAction),
    Authorizer: iauth.FA(iauth.FeatureAIIntent, iauth.ActionExport),
}

func ExportAction(req *http.Request) (interface{}, error) {
    param, err := export_util.NewExportFromReq(req) // 解析 version
    if err != nil {
        return nil, err
    }
    return container.IntentConfigManager.ConfigExport(req.Context(), param.Version)
}
```

conf-agent 侧登记（`conf-agent.toml`，非本仓库代码改动）：`[Reloaders.mod_ai_intent]`：拉取 `/inner-api/v1/configs/mod-ai-intent` 落盘 `conf/mod_ai_intent/intent_questions.data`，`BFEReloadAPI = "/reload/mod_ai_intent"`。

## 7. 静态 conf 不下发

`mod_ai_intent.conf`（决策服务地址/超时/缓存/熔断/显式头名）属部署期静态配置，**不进本接口下发链路**，经 conf-agent `CopyFiles` 下发。理由同 ai_cache 的"Redis 连接配置不下发"原则：

- 连接/环境信息与配置数据生命周期不同（近乎不变）；
- 减少决策服务地址等部署信息在导出链路中的暴露面；
- 与 `mod_ai_cache.conf` / `mod_ai_rate_limit.conf` 同款。

本方案只下发 `intent_questions.data` 一个数据文件。

## 8. 与 ai_cache_rules 导出的差异

| 维度 | ai_cache_rules 导出 | intent_config 导出 |
|------|---------------------|---------------------|
| 资源形态 | 集合（有序规则数组） | 全局单例（单行覆盖） |
| 写入语义 | 事务内 delete-all + insert-all 整体重建 | 单行 upsert 覆盖（固定 `id=1`） |
| Generator 数据源 | 查全表 `id` 升序 | `Fetch` 唯一行 |
| 无数据行为 | 空表导出空数组（product 键仍 present，值为 `[]`） | 无记录返回 nil（不导出，BFE 维持现状，`Data: null`） |
| 导出 Data 形态 | `Version` 外置 + `Config[product]` 包装（两段） | **Data = 文件内容原样**（`Version` 内嵌文件，同 ai-route 端点形态） |
| version 语义 | 导出侧 MD5 签名比对（内容未变返回旧版本） | 每次 PUT 必生成新 version；导出侧 version 与上次相同返回 nil——双端同语义 |
| 空配置语义 | `{"rules": []}` 清空规则 | `{"questions": []}` 软开关停用意图分类（正常下发） |
| enabled 过滤 | 无过滤，全表导出 | 无 `enabled` 概念 |
| 静态 conf | `mod_ai_cache.conf`（Redis 连接）经 `CopyFiles` 不下发 | `mod_ai_intent.conf`（决策服务地址/超时/缓存/熔断）经 `CopyFiles` 不下发 |
| 产物文件 | `ai_cache.data` | `intent_questions.data` |
| 版本控制 | `mod_ai_cache` topic | `intent_config` topic（独立版本线） |

## 9. 路由规则消费方式（cond 直传，无模型变更）

路由规则 OpenAPI 与存储**完全不变**：调用方在 `rules[].Cond` 中直接书写意图条件，控制面仅做语法编译校验（`lib/validate` 的 `ConditionExpression`，内部 `condition.Build`），原样存储、原样导出。示例：

```
req_ai_intent_in("task_type", "test_writing", 0.9) && req_ai_intent_in("complexity", "simple|medium")
```

书写约定（出自 BFE 侧文档，控制面只校验语法不校验语义）：

- 第一参：问题名，须与 `intent_config.questions[].name` 一致；引用了未配置的问题名 → 运行时该条件**永不命中**（fail-safe），规则 fall through 到下一条；
- 第二参：`|` 分隔的选项列表（choice 填选项名，score 填档位名）；
- 第三参（可选）：显式置信门槛；省略 = 用该问题 `min_confidence`；显式零写作 `0.0`（整数字面量 `0` 是 INT，会被 BFE 原型检查拒绝）。

**引用完整性不在控制面校验**（关键决策）：cond 中引用的问题名/选项由 BFE 运行时求值，未配置的问题名"永不命中"（fail-safe 语义），不报错不阻断；避免控制面与 BFE 配置状态的双端耦合；配置补齐后规则自动生效，无需改规则。

**前置依赖**：go.mod 的 bfe 依赖升级到含 `req_ai_intent_in` 的提交（fork v1.8.9-dev ≥ `7e482d90`）后，新原语的语法校验自动生效（`lib/validate` 零代码改动）；升级前含该原语的 cond 会被 `condition.Build` 拒绝。

BFE 侧完整语义见 `bfe/docs/zh_cn/condition/request/intent.md`。

## 10. 边界情况

| 场景 | 行为 |
|------|------|
| PUT `{"questions": []}`（空 questions 软开关） | 合法：停用意图分类——BFE 侧所有意图条件不命中、流量走默认路由；恢复 = 发布非空配置，路由规则无需改动 |
| GET 未发布过配置 | 404（尚未发布过意图配置） |
| InnerAPI 未发布 / 版本未变 | `Data: null`，conf-agent 不落盘、不触发 BFE `/reload/mod_ai_intent` |
| PUT 校验失败（questions 超 10、name 重复/为空、type 非法、criteria/levels 缺失或超项、选项名含 `\|`、min_confidence 越界） | 整个 PUT 400（`INVALID_ARGUMENT`），单行不变；同时记录一条失败审计 |
| BFE 热更校验失败（双端口径漂移） | BFE 拒绝加载、维持上一份生效配置；双端校验同口径 + 集成测试覆盖；回滚 = 重新 PUT 旧内容 |
| cond 引用未配置的问题名 | 语法校验通过；BFE 运行时该条件永不命中（fail-safe），规则 fall through 到默认规则；配置补齐后自动生效 |
| 手写 cond 语法错误 | `condition.Build` 存储前拦截（400，需 bfe 依赖已升级） |
| 旧 BFE 集群加载含新原语的规则 | 编译失败、规则不生效（BFE 加载期拒绝该规则）；升级 BFE 前不要对旧集群发布意图规则 |
| 无历史版本，误操作后无法直接回滚 | 操作日志/人工备份找回旧内容重新 PUT；或临时 PUT `questions: []` 软开关停用；发布前 GET 留存副本 |

## 11. 测试要点

- **manager 单测**：首次 PUT 插入单行（固定 `id=1`）、再次 PUT 覆盖且 version 更新、version 冲突 +1s 顺延、Fetch 无记录行为；
- **Generator 单测**：有/无记录、导出 version 未变返回 nil、`Questions` JSON 透传正确（marshal 结果做 JSON key 精确断言防回归）；
- **整体校验单测**：全分支（questions JSON 合法性、同口径校验项、空数组软开关语义）；
- **集成测试**：PUT intent-config → GET 回读 → InnerAPI 导出断言 JSON 契约（PascalCase、`Data` 即文件内容原样）；
- **路由集成**：含 `req_ai_intent_in(...)` 的 cond 规则在 bfe 依赖升级后通过校验并原样导出；旧版依赖下该 cond 被拒（升级前行为的反向断言）；
- **回归**：`make test-model-cover-gate`（model 覆盖率 ≥70%）；既有路由规则单测/集成（cond 直传链路行为不变）。
