# 报表查询模块

> 接口定义见 [api-define/OpenAPI接口定义/report.md](../api-define/OpenAPI接口定义/report.md)；变更记录见 [modifications/2026-09-15-report-query-api](../modifications/2026-09-15-report-query-api/change-summary.md)、[modifications/2026-09-27-report-cache-mirror-intent-fields](../modifications/2026-09-27-report-cache-mirror-intent-fields/change-summary.md)（缓存/镜像/意图字段消费，本文 §4.1）。

## 1. 背景与定位

数据报表原来依赖 Kafka → Doris → Grafana 链路。本模块为 ai-gateway-api 增加统一的报表查询能力（`/open-api/v1/report/*`），报表直接在 ai-gateway-web 展示，无需 Grafana。查询后端通过配置切换两种部署形态：

| 形态 | 链路 | 后端 |
|------|------|------|
| 轻量形态 | BFE → pb 日志 → log-reader(mod_log_mysql) → MySQL | `Backend = "mysql"` |
| 标准形态 | BFE → pb 日志 → log-reader(mod_kafka) → Kafka → Doris | `Backend = "doris"`（复用存量链路数据） |

两种形态共用一套 API、一套前端；写入侧（log-reader 插件）见 `log-reader/doc/modifications/2026-09-15-add-mod-log-mysql-plugin/design-changes.md`。

## 2. 模块结构（沿用三层分层惯例）

```
endpoints/openapi_v1/report/     # 路由与 Handler（xreq.Endpoint 声明式注册）
model/ireport/                   # ReportManager：参数校验、bucket 计算、口径常量、委托 storager
storage/mysqlreport/             # MySQL 实现（gendry builder）+ 聚合/分区 JOB
storage/dorisreport/             # Doris 实现（database/sql + mysql 协议驱动连 FE 9030）
stateful/                        # [Report] 配置段 + 按 Backend 装配
model/iauth/                     # FeatureReport 鉴权
```

## 3. 数据源与配置

复用 `stateful/config_database.go` 的 `Databases` 多数据源 map（`DbGet(name)` 按名取连接）；MySQL 与 Doris（FE MySQL 协议端口）都只是 map 条目，不引入新客户端。

`[Report]` 配置段（`conf/ai_gateway_api.toml`）：

```toml
[Report]
Backend = "mysql"             # mysql | doris；缺省时 Report 模块整体不装配，/report/* 不注册（404）
Datasource = "report_db"      # Databases 中的数据源名（doris 时填 doris_db）
Database = ""                 # 库名覆盖（可选，默认取数据源的 DBName）
EnableAggregateJob = true     # backend=mysql 时启用分钟聚合 JOB
AggregateIntervalSec = 60
RetentionDays = 7             # 明细保留天数（分区 DROP / DELETE 窗口）
EnablePartitionMgmt = true    # 分区管理 JOB（非分区表自动降级 DELETE）
```

## 4. ReportStorager 接口与 Manager 职责

查询层抽象 `ReportStorager` 接口（`model/ireport/types.go`），两后端各一套方言 SQL 实现：

```go
type ReportStorager interface {
    Overview(ctx context.Context, f *Filter) (*OverviewResult, error)
    TimeSeries(ctx context.Context, metric, dimension string, f *Filter, bucketSec int) ([]*MetricPoint, error)
    Rankings(ctx context.Context, dimension string, f *Filter, limit int) ([]*RankingItem, error)
    Distribution(ctx context.Context, dimension string, f *Filter) ([]*DistItem, error)
    Logs(ctx context.Context, f *LogFilter) (*LogQueryResult, error)
    Capabilities() *BackendCaps
}
```

`ReportManager`（`model/ireport/manager.go`）负责：

- 参数绑定校验（`go-playground/validator`，同 operation-logs 惯例）；`metric`/`dimension` 枚举校验；窗口 ≤7 天；
- 时间桶计算：≤6h→60s、≤3d→300s、≤7d→1800s；
- 指标口径常量（QPS = `SUM(request_count)/窗口秒数`；错误率 = `error_count/request_count`；平均延迟 = `all_time_sum/request_count`；TTFT/TPOT 聚合于 stream 请求、微秒→毫秒；成本按币种分组，定点值在 storager 出口统一 ÷1e8 换算为金额（元/美元），详见 `model/ireport/types.go` 的 `CostFixedPointToAmount`）；
- 后端能力门控（§4.1）：维度白名单校验后追加 `Capabilities()` 校验，后端不支持的维度返回 422；
- 委托 storager 执行，自身不含 SQL。

### 4.1 缓存/镜像/意图字段消费（2026-09-27 变更）

- **明细投影/过滤**：`LogRow` 投影明细表新增 10 列（`ai_cache_status`、`mirror_hit`、`mirror_cluster`、`ai_intent_question`、`ai_intent_answer`、`ai_intent_confidence`、`ai_intent_source`、`ai_intent_latency_us`、`ai_intent_cache_hit`、`ai_intent_questions_version`，列序与 `db_ddl_report_mysql.sql` 一致）；`LogFilter` 新增 `CacheStatus`/`MirrorHit`/`IntentQuestion`/`IntentAnswer`/`IntentSource` 五个精确匹配条件（`detailWhere` 派生），logs 端点绑定对应 query 参数（`cache_status`/`mirror_hit`/`intent_question`/`intent_answer`/`intent_source`），两后端均可用。
- **overview 新指标**：`cache`（hit/miss/skip 次数 + `hit_rate=hit/(hit+miss)`（skip 不计分母）+ `read_tokens`/`write_tokens`）、`mirror`（`hit_count`）、`intent`（`classified_count`/`unknown_count`/`unknown_rate`，口径为路由实际消费的意图）。命中/跳过/镜像/意图次数走明细表条件 COUNT（沿用 `logs_total` 模式），cache token 总量走聚合表 `cache_read_tokens`/`cache_write_tokens` SUM（既有列）。
- **时序**：新增 `cache_tokens` 指标（`cache_read`/`cache_write` 两条序列，`kind` 字段区分，UNION ALL 实现）；timeseries 端点新增**可选** `dimension` 参数（仅 `ai_intent_answer`/`ai_cache_status`/`mirror_hit` 三个值），传入后按 `(时间桶, 维度值)` 分组、点携带 `name` 区分序列。
- **排行/分布**：dimension 枚举新增 `ai_intent_answer`/`ai_cache_status`/`mirror_hit`；字符串维度空值不进排行、分布归一为 `unknown` 桶，`mirror_hit` 为数值维度（排行返回 `0`/`1` 桶、分布返回 `"0"`/`"1"` 桶）。
- **backend 能力门控**：`ReportStorager` 增 `Capabilities() *BackendCaps`（`Backend` + `SupportedDimensions`，backend 标识由 `initReport()` 装配时注入构造函数）。三个新维度一期仅 MySQL 后端声明；Doris 后端请求返回 422，错误信息 `dimension <name> not supported by doris backend (mysql only until doris support lands)`——杜绝"空报表"被误读为"没有数据"。二期 Doris 聚合表维度补齐后对齐并移除门控。

## 5. 两后端 SQL 方言差异

| 点 | Doris | MySQL |
|----|-------|-------|
| 时间桶 | `DATE_TRUNC(ts_min, 'minute')` / `FLOOR(EPOCH(hour)/bucket)` | `FROM_UNIXTIME(FLOOR(UNIX_TIMESTAMP(ts_min)/?)*?)` |
| 分位数延迟 | `PERCENTILE_APPROX(all_time, 0.5/0.9/0.99)`（明细表） | 无原生分位数：v1 只返回 avg/max（分位数近似方案待上线后按反馈决策） |
| 限流命中展开 | `CROSS JOIN UNNEST(ai_rate_limit_hits)` | MySQL 8.0 可 `JSON_TABLE`（v1 明细页不展开，仅展示 JSON 原文） |
| 过滤空值 | `ai_provider != ''` | `IFNULL(ai_provider,'') != ''`（明细 NULL 语义） |

时序/排行/分布只读聚合表（MySQL `bfe_ai_metrics_1m` / Doris 同名表），仅明细查询读明细表 `bfe_ai_request_log`。

## 6. 后台 JOB（仅 backend=mysql，`storage/mysqlreport/job.go`）

Go ticker 内嵌单协程，多副本部署用 MySQL `GET_LOCK('report_agg_job', 0)` 抢锁防重。

**分钟聚合 JOB**：每周期对「上一整分钟」窗口执行 `DELETE + INSERT SELECT`（单事务）——窗口重放幂等；维度 40 列写入时 `IFNULL(col,'')` 归一（与 Doris 聚合 JOB 的 COALESCE 语义一致；`mirror_hit` 归一为 0/1）；聚合表不设唯一键（40 维键超长且幂等由 JOB 事务保证）。

**分区管理 JOB**：每 6h 向前建 3 天分区、`DROP PARTITION` 超 `RetentionDays` 的分区；`information_schema.PARTITIONS` 探测非分区形态时降级 `DELETE ... LIMIT` 分批。MySQL 无动态分区，**必须先于数据到达建好分区**，否则写入被直接拒绝（Error 1526）；JOB 启动时立即补建一次。

## 7. 表结构与 DDL 归属

两张报表表（明细 `bfe_ai_request_log` 99 列 + 聚合 `bfe_ai_metrics_1m` 40 维 24 指标——2026-09-27 起含 `ai_cache_status`/`mirror_hit`/`ai_intent_answer` 3 个维度列，Doris 侧维度二期对齐）的 DDL 统一放本仓库 `db_ddl_report_mysql.sql`，随本仓库发布、部署流程执行（schema-first：先 DDL 后启用 log-reader 插件）；插件不自动建表。**表结构权威文档见 [报表库设计文档.md](../报表库设计文档.md)**。理由：ai-gateway-api 对 schema 依赖面最广（聚合 JOB 取数、分区管理 JOB、明细查询），且本仓库是唯一有 DDL 管理传统的仓库；log-reader 账号按最小权限原则仅对明细表有 INSERT/UPDATE，无 DDL 权限。

明细表 DDL 的三处要点已经过 log-reader LR03 集成测试（真实 MySQL 8.4）验证：

1. **长文本列用 TEXT**（origin_uri/final_uri/x_forward_for/authorization/referrer/user_agent/cookie/res_location）：utf8mb4 下 VARCHAR 总长度超 MySQL 65535 字节行上限（Error 1118）；
2. **幂等键字符串列 `ai_apikey_id`/`ai_requested_model` 允许 NULL**：写入侧零值规则把空字符串映射为 NULL（未认证请求即如此），`NOT NULL` 会使这类写入整批失败（Error 1048）；`hostid`/`log_time` 保持 `NOT NULL`；
3. **按天 RANGE 分区** + 唯一键 `(hostid, log_time, ai_apikey_id, ai_requested_model)`（与 Doris UNIQUE KEY 一致，log-reader 重发/`-b` 补读幂等）。

## 8. 鉴权

- `model/iauth/features.go` 新增 `FeatureReport`；
- `scope2permission`：System scope → `ReadAll`（当前 web 仅管理员，报表为管理员功能）；Product scope → `Read`（为租户自助用量报表预留的行级权限模型）；
- 所有端点 `Authorizer: iauth.FA(iauth.FeatureReport, iauth.ActionReadAll)`，无权限 402。

## 9. 装配与缺省行为

`stateful/container/rdb/components.go` 按 `[Report].Backend` 装配：mysql → `mysqlreport.New(DbGet(Datasource))` + 启动 JOB；doris → `dorisreport.New(...)`，不启动 JOB（Doris 聚合由既有 INSERT JOB 完成）。配置缺省时 Report 组件整体不装配，`/report/*` 路由不注册（404）——纯增量发布，不影响现有接口。

## 10. 风险

- **MySQL 容量**：建议 MySQL 形态目标量级 ≤ 日均百万级；超量走 Doris 形态；
- **聚合 JOB 多副本**：`GET_LOCK` 防重；多实例独立 MySQL 时各跑各的，无冲突；
- **双链路并存口径**：同一集群同时启用两种落库形态时两套报表可能不一致（log-reader 无持久化位点，既有短板）；部署上明确单集群单形态；
- **分位数缺失**：MySQL 后端无 P50/P90/P99，由返回字段有无驱动前端降级。
