# 操作日志模块

## 1. 背景与目标

`ai-gateway-api` 作为 AI 网关的控制面，会频繁发生配置变更（创建/更新/删除 Entity、Cluster、Route、API-Key 等）。这些变更是故障追溯、安全审计、合规检查的关键依据。操作日志模块的目标是：

- 记录所有会产生写操作的配置变更；
- 区分成功与失败操作，保留失败审计证据；
- 对敏感字段脱敏，避免日志泄露；
- 采用异步批量写入，尽量降低对主业务请求的延迟影响；
- 提供结构化查询接口 `GET /open-api/v1/operation-logs`。

## 2. 总体架构

操作日志模块位于 `model/ioperlog`，向下通过 `storage/rdb/ioperlog` 落库，向上为各业务 Manager 提供 `OperationLogRecorder` 接口。

```
endpoints/openapi_v1/operation_log
        │
        ▼
   model/ioperlog
   ├─ types.go      # 数据类型与接口
   ├─ manager.go    # 异步缓冲 + 批量写入 + 查询
   ├─ mask.go       # 敏感字段脱敏
   └─ helper.go     # 错误信息截断等工具
        │
        ▼
   storage/rdb/ioperlog
   └─ operation_log.go  # DAO 封装
```

各业务 Manager 在 `stateful/container/container.go` 中通过 `SetOperationLogManager` 注入 `OperationLogManager`。

## 3. 核心数据模型

### 3.1 `OperationLogEntry`

```go
type OperationLogEntry struct {
    ID               int64
    LogID            string
    OperatorType     OperatorType // 0=user, 1=token
    OperatorID       int64
    OperatorName     string
    Action           string       // create/update/delete/reset/import/bind/unbind
    ResourceType     string       // entity/api_key/provider/cluster/...
    ResourceID       string
    ResourceName     string
    ResourceParentID string
    Status           int8         // 1=success, 2=failed
    ErrorMsg         string
    ChangeSummary    map[string]interface{} // 脱敏后的变更摘要
    RequestPath      string
    RequestMethod    string
    ClientIP         string
    UserAgent        string
    CreatedAt        time.Time
}
```

### 3.2 状态与动作常量

```go
const (
    StatusSuccess int8 = 1
    StatusFailed  int8 = 2
)

const (
    ActionCreate   ActionType = "create"
    ActionUpdate   ActionType = "update"
    ActionDelete   ActionType = "delete"
    ActionReset    ActionType = "reset"
    ActionImport   ActionType = "import"
    ActionBind     ActionType = "bind"
    ActionUnbind   ActionType = "unbind"
)
```

## 4. 写入流程

### 4.1 成功路径

业务 Manager 在事务成功提交后，组装 `OperationLogEntry` 并调用 `Record`：

```go
m.recordClusterOperation(ctx, string(ioperlog.ActionCreate), clusterID, clusterName, nil, clusterParamToMap(param), nil)
```

此时 `Status = StatusSuccess`，`ErrorMsg` 为空。

### 4.2 失败路径

当写操作因参数校验、业务约束、数据库错误等原因失败时，在返回错误前调用同一函数并传入 `err`：

```go
err = cm.txn.AtomExecute(ctx, func(ctx context.Context) error {
    for _, checker := range cm.deleteCheckers {
        if err = checker(ctx, product, cluster); err != nil {
            return err
        }
    }
    // ...
})
if err != nil {
    cm.recordClusterOperation(ctx, string(ioperlog.ActionDelete), cluster.ID, cluster.Name, clusterToMap(cluster), nil, err)
    return err
}
```

`recordClusterOperation` 内部根据 `err != nil` 设置 `Status = StatusFailed`，并调用 `ioperlog.TruncateErrorMessageDefault(err)` 填充 `ErrorMsg`。

### 4.3 错误信息截断

`operation_logs.error_msg` 字段为 `varchar(1024)`。`TruncateErrorMessage` 将超过长度的错误信息截断并追加 `...` 省略标记，避免数据库写入失败。

```go
func TruncateErrorMessage(err error, maxLen int) string
func TruncateErrorMessageDefault(err error) string // maxLen = 1024
```

## 5. 异步批量机制

`OperationLogManager` 采用内存缓冲通道 + 后台批量 worker：

- 缓冲通道默认容量 `4096` 条；
- 批量大小默认 `200` 条；flush 超时默认 `5s`；
- `Record(ctx, entry)` 先由 `ContextExtractor` 从 `ctx` 注入 `log_id`、请求路径、客户端 IP 等请求级字段，再投递到缓冲通道；
- 缓冲满或关闭时降级为同步写入；写入失败重试 3 次，仍失败则记录 error log；
- 进程退出时 `Close()` flush 缓冲区剩余日志。

失败日志与成功日志走同一条异步通道，不阻塞业务返回。

## 6. 敏感字段脱敏

`model/ioperlog/mask.go` 提供统一脱敏函数：

```go
func MaskAPIKeyToken(token string) string
func MaskString(string) string
func MaskSensitiveFields(data map[string]interface{}) map[string]interface{}
func MaskErrorMessage(msg string, values ...string) string
```

脱敏规则：

| 字段 | 规则 |
|------|------|
| `password`、`secret`、`session_key`、`private_key`、`token`、`access_token`、`client_secret`、`secret_key`、`access_key` 等 | 替换为 `******` |
| `api_key`、`apikey`、`key`（字符串类型） | 保留前 4 位和后 4 位，中间用 `****` 替代 |
| `certificate`、`cert_body`、`private_key_body` 等 | 替换为 `[已更新]`，不记录具体内容 |
| 嵌套 map | 递归脱敏 |
| `[]interface{}` 数组 | 逐元素递归，元素为 map 时按上述规则脱敏（如 provider `keys[].key`） |
| `error_msg` 自由文本（api_key 域） | 对错误消息中已知的 API-Key 值做值级精确替换，掩码形态同 `key` 行；兜住 DAO 驱动错误等未预见回显路径（issue #185） |

各业务 Manager 通过 `model/ioperlog/change_summary.go` 提供的 `BuildChangeSummary` 统一构造 `change_summary`，该函数会：

- 对 `before` / `after` 调用 `MaskSensitiveFields` 完成脱敏；
- 对 `update` 动作计算并写入 `diff_keys`，用于详情页展示差异字段；
- `diff_keys` 按 `after` 中存在的 key 与 `before` 比较，值不同或 `before` 不存在时计入差异，并按字母序排序。

`before` / `after` 由各域 `*ParamToMap` 从参数结构构造，快照键名与值表示遵循资源 Open API 词汇，消费方可按 API 字段名解析（issue #205）。marshal 模式（`json.Marshal`→`Unmarshal` 往返）统一经 `model/ioperlog/param_to_map.go` 的 `ParamToMap`：nil 值键（部分更新中省略的字段）不物化为 null，避免幻影 diff（issue #201，覆盖 api_key / provider）；显式零值（如 `enabled=false`）为非 nil，仍保留并计入 diff。手写 nil-guard 域中，entity、route_rules、quota、iauth、iprotocol、iroute_conf、rate_limit_policy 直接映射字段；cluster（`model/icluster_conf/cluster_operation_log.go`）因模型词汇与 API 词汇不是大小写关系（`SessionSticky`→`enabled`、`MaxRetryInSubcluster`→`max_retry_in_cluster` 等），手写映射额外承载三项语义——API 词汇对齐（顶层 + 全嵌套）、`sticky_sessions.hash_strategy` 枚举整数→字符串翻译与 `epp_config` 原始串→JSON 对象解码、`ID`/`Ready`/`ProductID`/`Scheduler`/`SubClusters` 等 API 未暴露的内部记账字段裁剪（issue #205）。快照值一律保持纯 JSON 类型（map / 数组 / 标量），保证 `MaskSensitiveFields` 的递归脱敏全覆盖。

失败审计的 `error_msg` 在截断（`TruncateErrorMessageDefault`）之后，由 api_key 域在 `recordAPIKeyOperation` 中调用 `MaskErrorMessage` 以其资源持有的 Key 值做值级脱敏，与 `change_summary` 同契约（issue #185）；其余接入域的错误消息当前不回显凭证值，暂不接线。

每个域的 `operation_log.go` 提供类似如下私有函数：

```go
func (m *XxxManager) recordXxxOperation(
    ctx context.Context,

```

函数内部统一根据 `err` 设置 `Status` 与 `ErrorMsg`。

> 说明：`quota_plan` 与 `rate_limit_policy` 在上表中列为独立域，但其写操作实际由 Entity / API Key 生命周期嵌套触发（见 §7.1）。 manager 直连 storager 的 CRUD 方法仅承载独立路径审计，嵌套路径经 Auditor 接口记录（issue #161 前嵌套路径直连 storager 绕过审计层，产生归属缺失缺陷）。

### 7.1 嵌套资源审计与归属（issue #161）

Entity / API Key 的创建、更新、删除会在同一事务内级联写 `quota_plan` / `rate_limit_policy`（storager 直连，保持原子性）。这类嵌套写操作的审计采用**写/审分层**模式：

- **归属类型**：`model/shared/operation_audit.go` 定义 `ResourceOwner{Type, ID}`，ID 为 owner 业务 ID，写入日志 `resource_parent_id`。归属类型与 Auditor 接口放在 `shared` 是因为依赖方向为 `quota/rate_limit_policy → entity/api_key`（余额同步等），owner 侧反向引用会成环。
- **Auditor 接口**：`shared.QuotaPlanAuditor` / `shared.RateLimitPolicyAuditor` 暴露 `AuditQuotaPlanCreate/Update/Delete` 等方法（成功与失败均记录，失败时 planID 传 0 避免引用回滚行）。由 `QuotaPlanManager` / `RateLimitPolicyManager` 实现，作为嵌套审计的**唯一入口**，快照构造复用各域 `xxxParamToMap`。
- **接入点**：`EntityManager` / `APIKeyManager` 在**事务外**与自身操作日志同点调用 Auditor（成功在提交后、失败在返回时），避免事务内随写记日志在后续回滚时残留"成功日志"。owner 来源：create/update 从请求侧解析（Entity ID 序列表预分配、API Key ID），delete 从库中快照取；旧快照（before）随 `oldEntity` / 事务内软获取，获取失败仅 before 为空。
- **reset 路径**：手动 reset 是唯一不经嵌套的 manager 直达路径，`ResetBalance` 签名接收 owner，两个 reset 端点透传 URI 中的 owner ID（修复前 `resource_parent_id` 恒为空串）。
- **装配**：`stateful/container/rdb/components.go` 在创建 `QuotaPlanManager` / `RateLimitPolicyManager` 之后，通过 `SetQuotaPlanAuditor` / `SetRateLimitPolicyAuditor` 注入 Entity / API Key Manager；未注入（如单测）时跳过嵌套审计，行为同旧。

## 8. 查询接口

`GET /open-api/v1/operation-logs` 提供按以下维度过滤：

- `operator_name`：操作人名称模糊匹配
- `action`：操作动作
- `resource_type`：资源类型
- `resource_id`：资源业务 ID
- `resource_parent_id`：资源父级业务 ID（如嵌套配额计划所属 Entity / API Key ID，issue #161）
- `status`：`1` 成功，`2` 失败
- `start_time` / `end_time`：时间范围
- `page` / `page_size`：分页

返回字段包含 `status`、`error_msg`、`change_summary`、`request_path` 等。

### 8.1 分页查询：延迟关联（issue #275）

25 万行规模下，`SELECT * … ORDER BY created_at DESC, id DESC LIMIT offset,n` 的 offset 语义要求先产出并丢弃前 offset 行，`SELECT *` 使每一跳按主键回表物化整行（`change_summary` 为 mediumtext），深页耗时随 offset 线性增长（末页 14–20 s）。修复后列表查询改为**延迟关联**（deferred join）：

```sql
SELECT t.* FROM operation_logs t
JOIN (
    SELECT id FROM operation_logs
    WHERE <全部过滤条件>
    ORDER BY created_at DESC, id DESC
    LIMIT ?, ?          -- offset, page_size
) x ON t.id = x.id
ORDER BY t.created_at DESC, t.id DESC;
```

- 内层在 `idx_created_at`（或"过滤列 + `created_at`"组合索引：`idx_operator_name_created` / `idx_status_created` / `idx_resource_name_created` / `idx_resource_id_created`）上做覆盖索引反向扫描，只取 id 不回表；外层 `eq_ref` 主键查找仅回表本页 `page_size` 行；
- MySQL 不接受带 `LIMIT` 的 IN 子查询（ERROR 1235），id 集合必须来自 JOIN 派生表；
- 外层必须显式重排序（JOIN 不保证行序），保持 `created_at DESC, id DESC` 契约；
- 内层 SQL 仍由 gendry 编译（过滤值全部占位参数化），外层模板拼接，经 `stateful.SQLRecord` 埋点；
- `TOperationLogCount` 同样补了 SQLRecord 埋点，`count(*)` 可在 `/monitor/metrics` 观察到；
- `offset >= total` 时短路返回空页，不触碰数据表——越界页（如 `page=9999999`）不会退化为全表扫描。

接口契约不变：任意 `page>0` 均为合法请求，`pagination.total` 仍为完整过滤集合计数。

### 8.2 过滤索引的存量迁移与计数缓存（issue #280）

#275 把过滤列组合索引写进了全量建库脚本（`db_ddl.sql`），但增量升级脚本 `database/db_ddl_upgrade_to_0.0.11.sql` 未包含对应 `ALTER`，按脚本升级的存量库过滤查询仍全表扫描（25 万行规模首页 3.6–20 s）；`resource_id` 单独过滤也因 `idx_resource` 前导列为 `resource_type` 而无索引可用。修复分两部分：

- **存量迁移**：升级脚本追加 §5，一次 `ALTER TABLE` 加 4 个组合索引（#275 的 3 个 + 新增的 `idx_resource_id_created`），显式 `ALGORITHM=INPLACE, LOCK=NONE`；`db_ddl.sql` 同步补第 4 个索引。至此全部文档化过滤列均有可用索引，任意合法过滤组合不再可能全表扫描。
- **计数缓存**：`storage/rdb/ioperlog` 的 `List` 中 `pagination.total` 按过滤条件（不含分页参数）哈希为 Redis key（`OPERLOG_COUNT:G<世代>:<sha256>`，TTL 10 s），同一过滤条件翻页不再重复 `count(*)`；每次异步批量刷盘成功后 `Incr` 世代键（`OPERLOG_COUNT_GEN`），旧世代缓存条目不可达、随 TTL 过期。未配置 Redis 时由 `MockRedisClient` 进程内兜底；任何 Redis 故障自动降级为实时计数。值为精确计数而非近似值：刷盘前缓冲中的日志对实时 `count(*)` 本就不可见，而已落盘写入会立即使缓存失效，故缓存值与实时计数的一致性等价。

## 9. 失败日志的特殊处理

### 9.1 变更摘要

- **Create 失败**：保留请求入参（`after`），帮助定位参数校验失败。
- **Update 失败**：若已查询到旧值，保留 `before`；否则仅记录请求入参。
- **Delete 失败**：保留被删除对象的旧值（`before`）。

### 9.2 幂等性与重试

同一操作的多次失败会产生多条失败日志，每条日志独立记录一次失败尝试，符合审计需求。

### 9.3 敏感信息

`ErrorMsg` 直接记录 `err.Error()`。若后续有合规要求，可在 `TruncateErrorMessage` 中扩展敏感词过滤。

## 11. 边界情况与注意事项

- **避免循环**：记录失败日志时不应触发新的业务校验或写操作。
- **队列压力**：失败日志数量通常远低于成功日志，异步缓冲队列压力可忽略。
- **字段长度**：`error_msg` 写入前必须截断，防止超长导致数据库错误。
- **接口兼容**：`OperationLogRecorder.Record` 接口不变，新增失败日志不需要修改容器注入。
