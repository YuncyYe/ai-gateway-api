# 批量任务与对账

## 1. 概述

批量与异步任务支持（一期：批量透传正确化）让 provider 原生 OpenAI Batch API（`/v1/files` + `/v1/batches`）经过网关时"计费正确、可管控"。BFE 数据面（`mod_ai_batch` + `mod_ai_token_auth` 批量分支）负责端点识别、批量查价、预留/结算/释放执行与 `BATCH_*` Redis 键维护；本文档描述 **ai-gateway-api 控制面**的配套机制：

- `batch_files` / `batch_tasks` 两表：批量任务在控制面的权威实体（另见《数据库设计文档.md》6.14 / 6.15）。
- `model/ibatch`：任务查询、cancel、对账 job（Manager + Storager 模式）。
- `endpoints/openapi_v1/batches/`：4 个管控端点。
- 导出变更：`ModelTable` 批量价展开行、`ai_rate_limit.data` 策略 `rules.batch` 段。

需求与主设计：`document-ai-gateway/迭代系统设计/v0.8/批量与异步任务支持/`；变更记录：`design-docs/modifications/2026-10-07-ai-batch-support/`（`api-changes.md` / `design-changes.md` / `change-summary.md`）。

## 2. 背景：BFE 侧与 Redis `BATCH_*` 键结构

BFE 与控制面共享同一 Redis 集群（与 `QUOTA_*` 同集群、同 1e-8 定点口径）。数据面 `mod_ai_batch` 在请求链路中维护以下键（**as-built 契约**，以 `bfe/bfe_modules/mod_ai_batch/batch_state.go` 与 `mod_ai_token_auth/batch_quota.go` 为准），控制面全部机制围绕这些键展开：

| 键 | 类型 | 内容 | TTL |
|----|------|------|-----|
| `BATCH_FILE:<cluster>:<file_id>` | HASH | `{api_key_id, key_name, cluster, lines, bytes, purpose, dir, filename, batch_id, lines_src, bytes_src}` | 48h |
| `BATCH_TASK:<batch_id>` | HASH | `{api_key_id, cluster, key_name, input_file_id, output_file_id, endpoint, request_counts, est_lines, reserved_units, reserved, status, created_at, usage_in, usage_out, settle_units, settle_status, usage_source}` | 48h |
| `BATCH_RESERVE:<api_key_id>` | 计数 | 预留占用镜像计数（可用余额 = `QUOTA_*` 剩余 − 本计数） | 随任务生命周期 |
| `BATCH_RESERVE_BATCH:<batch_id>` | HASH | `{planRedisKey -> 各配额计划预留 units}`，按 batch 逐计划簿记；释放/结算原子扣镜像 + 删簿记，簿记空即幂等（token_auth 侧） | 随任务生命周期 |
| `BATCH_SETTLED:<batch_id>` | STRING `"1"`，SET NX EX | 结算/释放共用去重占位（下载拦截与对账 job 兜底两个触发点共用） | 48h |
| `BATCH_ACTIVE:<api_key_id>` | ZSET | member=batch_id，score=created_unix；`max_active_batches` 限流维度 | 随任务生命周期 |

要点：

- `BATCH_FILE` / `BATCH_TASK` 键中段为**路由 cluster 名**（BFE 运行时概念，控制面无 provider↔cluster 映射需求时由 DB 的 provider 列直接承载读回值）；hash 内亦无 product/entity 字段，同步落库与 Redis 回源时经 api_key 解析补齐租户字段。
- `BATCH_TASK` hash 内含任务同步全部字段；BFE 在下载拦截结算时**原地更新** `usage_in/usage_out/settle_units/settle_status=settled/usage_source=download`，控制面对账 job 从本键直接取用同步落库——**Redis 是任务同步的主事件源，不是报表库、也不是访问日志管道**。
- `lines`/`bytes` 描述**文件内容**（不是 multipart 信封）；`lines_src`/`bytes_src` 为 `exact`/`approx`，标 `approx` 表示数据面只能从整包计数推断（chunked/超大上传），控制面据此判断行数口径是否可用于预扣核对。
- `request_counts` 为 provider 返回的 JSON 对象**原样串**；`created_at` 为 provider 的 unix 秒；`output_file_id`/`endpoint` 在 create/poll 任一步拿到即写入（空值不覆盖已有字段）。
- 键自然消亡后，任务实体以 `batch_tasks` 表为权威。

## 3. 任务实体与状态机

### 3.1 实体

`batch_tasks` 为权威任务实体（`idem_key = batch_id` 唯一，幂等落库定位键）；`batch_files` 为文件元数据（`(file_id, provider)` 唯一）。字段、约束与索引导见《数据库设计文档.md》6.15 / 6.14。

对外形状：`/batches` 三个 OpenAPI 端点的响应由 `endpoints/openapi_v1/batches/view.go` 的显式视图（`batchTaskView`）投影，零值 / 空值按 `batches.md` §2.1"字段必现规则"显式输出——内部模型 `ibatch.BatchTask` 的 `omitempty` tag 不决定对外契约（issue #271）。

### 3.2 状态机

状态对齐 OpenAI Batch API，provider 返回状态**原样存储、终态不回退**：

```
validating → queued → in_progress → finalizing → completed
                                ↘ expired / failed / cancelled
cancel（控制面/客户端受理）→ cancelling ─→（provider 确认）cancelled / completed
```

- 终态：`completed` / `expired` / `failed` / `cancelled`（`cancelling` 为受理中中间态，非终态）。
- cancel 后 provider 实际跑完（`cancelling → completed`）按 completed 正常结算。
- 二期方言（Anthropic `ended`、Gemini `deleted`）为枚举增量，不改表结构。

## 4. 三态对账（预留-结算-释放）

`settle_status` 是三态对账主字段（`reserved` / `settled` / `released`），金额为 1e-8 定点整数、单位 RMB，与数据面、配额（`QUOTA_*` / `quotacache`）同口径。

| 阶段 | 触发 | 行为 | settle_status |
|------|------|------|---------------|
| 预留 | 批量创建（BFE，两阶段：余额预检 → 上游 2xx 后预留） | 预留额 = 文件行数 ×（预估 input + 预估 output token 上限）× batch 单价；预估上限取价格行 `limits.max_input_tokens/max_output_tokens`，缺失回落 `mod_ai_batch.data` 默认（8192/4096）；`BATCH_RESERVE` 镜像计数 | `reserved` |
| 结算 | 下载输出文件（BFE 下载拦截解析 jsonl usage）或 job 兜底结算 | 按结果文件逐行 `response.usage` 汇总 × batch 价实结实扣；**允许透支预留**（低估不静默截断），超出打 `over_reserved=1` 进对账报表；`SETNX BATCH_SETTLED` 去重 | `settled` |
| 释放 | cancel 受理 / `expired` / `failed`（无结果文件） | 整额释放预留（`BATCH_RESERVE` 占用清零，幂等） | `released` |

completed 不直接释放：先按实结金额结算，预留随结算差额自然冲正。

控制面只经两条路径推进三态：

1. **cancel 端点**（§6）：抢占成功即置 `cancelling` + 幂等释放预留（终态由 provider 状态推进确认）。
2. **对账 job 兜底结算**（§5 职责③）：`completed 且 settle_status='reserved' 且超 30min 宽限` → 用 `key_name` 对应 provider key 下载输出文件解析 usage，直写 Redis 结算（`BATCH_SETTLED` 幂等）+ 条件更新 `settled`；终态且无结果文件 → `released`。

两条路径均以 `WHERE settle_status='reserved'` 条件更新推进——**条件更新本身是并发防线**，多实例/重跑不会双倍结算。

## 5. 对账 job（`model/ibatch/job.go`）

每分钟 tick，复用 `storage/mysqlreport/job.go` 的 named lock + 循环框架：MySQL `GET_LOCK` 多副本互斥；SQLite 模式 named lock 退化为空操作、约定单实例（与现有报表 job 同一约定）。

### 职责①：Redis 同步落库（主事件源）

SCAN `BATCH_TASK:*` / `BATCH_FILE:*`，按 `idem_key` / `(file_id, provider)` 幂等 upsert 落库；BFE 已把结算/释放字段原地更新进 `BATCH_TASK`，job 直接取用刷新 DB。键 TTL 48h ≫ 同步周期 1min，无丢失窗口。**不读报表库**——报表后端可插拔（§7），不能作为管控链路依赖。

### 职责②：状态推进

非终态任务直调 provider `GET /v1/batches/{id}`（用 `key_name` 出网），更新 `status` / `output_file_id` / `request_counts` / `endpoint`；首次发现 `output_file_id` 补登记输出 `batch_files`（`direction=output`）。幂等：upsert 天然可重入。

### 职责②b：终态产物补漏

设计意图（"终态任务的产物字段必须可补"）在主链路成立不了：职责① 的 Redis 同步会把 `completed` 直接落库，职责② 只查非终态，于是已终态的行永远补不上 `output_file_id`/`request_counts`。因此增加一轮补漏：

- 候选：`status='completed'` 且 `created_at` 在 24h 内，每轮上限 `advance_limit`，内存过滤"缺 `output_file_id` 或缺 `request_counts`"；
- 行为：直调 provider，只 patch 缺失字段（不改 `status`）；404/非 2xx/解析失败一律告警跳过（completed 不会因为 provider 侧过期被降级）；
- 代价：provider 永久缺失的行按周期重复出网，上限是"每轮 `advance_limit` 次 GET × 24h 窗口内缺失行"；需要退避时再引入尝试次数字段（遗留）。
- 备用性：数据面修复后新批次由 Redis 同步即可补齐，本职责主要覆盖"键先于同步到期"与历史缺字段的行。

### 职责③：兜底结算

`completed 且 settle_status='reserved' 且超宽限（30min）`（下载拦截因故未触发/失败）→ 控制面用 provider key 下载输出文件、流式解析 usage，直写 Redis 结算（`BATCH_SETTLED` 幂等）+ 条件更新 `settled`（`usage_source='reconcile'`）；`expired`/`failed`/`cancelled` 且无结果文件 → 条件更新 `released`。`WHERE settle_status='reserved'` 保证多实例/重跑不双倍结算。

**usage 解析口径与安全阀**：结果文件每行的 usage 位于 `response.body.usage`（OpenAI 契约），顶层 `response.usage` 作为兼容回退；`response:null` 的错误行不计。**安全阀**：若整份文件一个可计费行都没有、却存在"有 `response` 但没有 usage"的行（`parsedLines == 0 && noUsageLines > 0`），本轮**不推进 `settled`**——告警并释放 `BATCH_SETTLED` 占位，下轮重试。只有纯错误行/空文件（`parsedLines == 0 && noUsageLines == 0`，全部请求失败或结果为空）才按 0 元正常结算。这道阀防止解析口径漂移被固化成"0 元终态"。

### 职责④：对账巡检

- **占用核对**：Redis `BATCH_RESERVE` 占用 vs DB 在途任务 `reserve_units` 总额，差异告警。
- **金额核对**：以 `batch_tasks.settle_units` 为基准，与日志后端 batch 成本抽样比对（误差应为 0；非 MySQL 报表后端降级为按日任务级比对）。
- **日志补登**：读取日志后端带 `batch_id` 的批量行，对 DB 与 Redis 均缺失的任务（BFE Redis 写失败的 fail-open 场景）补登 `batch_tasks`（`sync_source='log'`）+ 告警；日志后端不可用时跳过、仅告警。

### 职责⑤：TTL 清理

终态任务保留 N 天（retention 可配），超期删除；Redis `BATCH_*` 键靠 TTL 自然消亡。API-Key / 产品线删除后的批量数据残留由本职责收敛（批量两表无导出、无物理外键）。

## 6. cancel 五步流程与竞态

### 6.1 五步流程

`POST /open-api/v1/batches/{batch_id}/cancel`（控制面直调 provider，不过数据面）：

1. **查任务**：DB → Redis `BATCH_TASK` 回源 → 均 miss 返回 404 `BATCH_NOT_FOUND`。
2. **取 key 拼地址**：按 `provider` 取 provider 记录与 `key_name` 对应 key 明文，实例地址 + `protocol_paths.openai` 拼 cancel URL。
3. **出网 POST provider cancel**：provider 不可达 502 `UPSTREAM_UNREACHABLE`；provider 返回批量不存在 404 `BATCH_NOT_FOUND`（透传 provider 语义）。
4. **抢占 + 释放**：DB 条件更新 `SET status='cancelling' WHERE batch_id=? AND status NOT IN (终态)`——**affected_rows=0 返回 409 `BATCH_TERMINAL_OR_CONFLICT`**（任务已终态或他实例处理中）；成功则 Redis 幂等释放预留。
5. **审计**：`operation_logs` 记录（change_summary 带 batch_id 与前后状态）。

### 6.2 竞态收敛：两把幂等锁

cancel 与对账 job（兜底结算/状态推进）、cancel 与 cancel 之间共用两把锁，均收敛：

| 锁 | 形态 | 防什么 |
|----|------|--------|
| `BATCH_SETTLED:<batch_id>` | Redis SETNX | 结算双倍：下载拦截结算 vs job 兜底结算 vs cancel 后 provider 跑完再结算，任一先占即去重 |
| `reserved_units 清零`（`BATCH_RESERVE` 释放的 Lua 原子语义） | Redis Lua 原子 | 释放双倍：cancel 释放 vs `expired/failed` 释放 vs job 释放，原子清零只生效一次 |

`settle_status='reserved'` 的 DB 条件更新是第三道防线：锁失效双跑时，后跑者条件更新 affected_rows=0 自然落空。cancel×cancel 由第 4 步 DB 抢占（affected_rows=0 → 409）互斥。

## 7. 与报表后端解耦

对账 job **不读报表库**，金额核对只以"日志后端带 batch_id 的批量行"做抽样比对，理由：

1. **报表后端是可插拔配置**（`[Report].Backend`：MySQL / Doris / ClickHouse / StarRocks），管控链路（任务查询/取消/对账）不能把可用性绑在可插拔组件上。
2. 报表管道（log-reader → 报表库）面向成本报表，字段映射与加列节奏由 observability 仓库独立演进；管控闭环要求字段稳定（`batch_id` / `usage` / `settle` 标记）。
3. Redis `BATCH_TASK` 已内嵌任务同步全部字段且 BFE 原地更新，时效（分钟级）优于日志管道；日志后端只在 Redis fail-open 缺失时做补登源与抽样核对源。

报表侧的批量口径（`bfe_ai_request_log` 加列、`batch_savings` 派生指标）见 `design-changes.md` §7，属 `model/ireport` / observability 仓库范围。

## 8. 多实例机制

| 组件 | 协调机制 | 失效/退化行为 |
|------|----------|----------------|
| 管控读接口（列表/详情/文件） | 无状态；DB/Redis 共享 | — |
| cancel 并发 | DB 条件更新抢占（affected_rows=0 → 409） | 与 keyrotate 锁表 409 先例同思路 |
| 对账 job | MySQL `GET_LOCK` named lock，每 tick 抢锁 | 锁失效双跑时全部写操作幂等收敛：SCAN upsert、`BATCH_SETTLED`、条件更新 settle 状态——最坏重复一次幂等操作，**不双倍结算** |
| 结算/释放 | Redis 原子锁（Lua）+ DB 条件更新 | 同上 |
| SQLite 部署 | named lock 退化为空操作，约定单实例 | 与现有报表 job 同一约定 |

原则：跨实例协调状态一律放 Redis（原子 Lua）或 DB（条件更新/named lock），**进程内不保留批量任务状态**；manager 依赖注入（AGENTS.md），测试可 mock。

## 9. 降级路径

cancel 与兜底结算共用**控制面 → provider 出网**能力（新 egress 依赖，部署文档放通说明）。不允许出网的部署降级：

| 能力 | 降级形态 | 影响 |
|------|----------|------|
| cancel | 退化为仅展示（不提供取消操作） | 任务只能等 provider 侧过期/完成 |
| 兜底结算（job 职责③） | 退化为只依赖下载拦截结算 + 预留 TTL 释放 | 下载拦截失败的 completed 任务对账精度下降（金额核对以日志后端为准） |
| 状态推进（job 职责②） | 不可用时任务状态停留于最后同步值 | 详情查询仍可靠，终态确认延迟 |

管控读接口与 Redis 同步落库不依赖出网，不受影响。

## 10. 边界情况

| 场景 | 行为 |
|------|------|
| 任务在 Redis 未落库窗口被查询 | 详情 DB miss → 回源 Redis `BATCH_TASK` 命中返回；再 miss 404 |
| cancel 时任务已终态 / 他实例正在 cancel | DB 抢占 affected_rows=0 → 409 `BATCH_TERMINAL_OR_CONFLICT` |
| cancel 后 provider 实际跑完 | `cancelling → completed` 正常按实结结算（不释放） |
| 预留低估（实际 usage 超出预留） | 照实结算、允许透支，打 `over_reserved=1` 进对账报表（不静默截断） |
| BFE Redis 写失败（fail-open） | 任务未登记 → 对账巡检经日志后端补登（`sync_source='log'`）+ 告警 |
| 日志后端不可用 | 补登跳过、仅告警；其余 job 职责不受影响 |
| `batch_limits` 全空 | 策略不参与批量限流；批量流量仍受 BFE `mod_ai_batch.data` 全局硬顶约束 |
| 未配置 batch 价 | 数据面查价 miss 计 0 费 + `PriceLookupMiss` 计数告警，不回退 chat 价 |
| Redis `BATCH_*` 键 TTL 消亡 | 任务实体以 DB 为权威；对账不受影响 |
