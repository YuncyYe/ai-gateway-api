# 限流策略与导出

## 1. 概述

限流策略用于控制 API-Key 或 Entity 对后端 AI 模型的访问速率。策略支持三类限制：

- **TPM**（Tokens Per Minute）：每分钟 Token 消耗上限；
- **RPM**（Requests Per Minute）：每分钟请求次数上限；
- **并发数**（Max Concurrency）：同时处理的请求数上限。

每个 API-Key 或 Entity 可绑定一个限流策略；在导出到 BFE 时，策略按 Entity 层级向上合并，最终生成 `rate_limit_policies` 与 `api_key_rl_policy_bindings` 两类配置。

---

## 2. 数据模型

### 2.1 表结构

```sql
CREATE TABLE rate_limit_policies (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(255) NOT NULL,
    description VARCHAR(255) DEFAULT NULL,
    product_name VARCHAR(255) NOT NULL,
    enabled TINYINT(1) NOT NULL DEFAULT 1,
    max_concurrency INT DEFAULT NULL,
    tpm_configs JSON DEFAULT NULL COMMENT 'TPM 配置数组',
    rpm_configs JSON DEFAULT NULL COMMENT 'RPM 配置数组',
    create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);
```

### 2.2 JSON 字段结构

#### `tpm_configs`

```json
[
    {
        "name": "tpm_gpt4",
        "model": "gpt-4",
        "window_minutes": 1,
        "max_tokens": 100000,
        "step_minutes": 1
    },
    {
        "name": "tpm_default",
        "model": "*",
        "window_minutes": 1,
        "max_tokens": 500000,
        "step_minutes": 1
    }
]
```

#### `rpm_configs`

```json
[
    {
        "name": "rpm_gpt4",
        "model": "gpt-4",
        "window_minutes": 1,
        "max_requests": 1000
    },
    {
        "name": "rpm_default",
        "model": "*",
        "window_minutes": 1,
        "max_requests": 5000
    }
]
```

`model` 支持具体模型名或通配符 `*`（表示默认限制）。

#### `batch_limits`

批量任务限流段（可选，可空），支撑 `/v1/files`、`/v1/batches` 端点族：

```json
{
    "max_create_rpm": 60,
    "max_active_batches": 10,
    "max_file_bytes": 104857600,
    "max_file_lines": 1000000
}
```

四维度均按发起请求的 API-Key 计数、与 `model` 无关（批量创建请求体无 model 字段）；省略/`null` 表示该策略不参与批量限流，仍受 BFE `mod_ai_batch.data` 全局硬顶约束。该段属于共享 `RateLimitPolicy` 类型，独立策略资源与 API-Key / Entity 的内联 `rate_limit_policy.rules` 均可配置。

## 4. 创建与更新

### 4.1 校验规则

`RateLimitPolicyManager.CreateRateLimitPolicy` / `UpdateRateLimitPolicy` 会执行以下校验：

1. `product_name` 必须非空且存在；随着 Product Scope 收敛，OpenAPI 不再要求传入，建议存储层默认填充为 `AI_product`。
2. 策略级 `name` 在产品内唯一；
3. `max_concurrency` 必须 ≥ 0（为 0 时 BFE 可能视为不限制或禁止，取决于 BFE 实现）；
4. `tpm_configs` / `rpm_configs` 中的每条规则：
   - `name` 必填、非空、长度 1-128 字符；
   - `name` 字符集限制为 `[a-zA-Z0-9_-]`；
   - `name` 在同一 `RateLimitPolicy` 内唯一；
   - `model` 不能为空；
   - `limit` 必须 ≥ 0。
5. `batch_limits`（配置时）四个维度（`max_create_rpm`、`max_active_batches`、`max_file_bytes`、`max_file_lines`）必须 ≥ 0；`enabled=true` 时 `tpm_configs` / `rpm_configs` / `max_concurrency(>=0)` / `batch_limits` 四者至少配置其一。

### 4.2 启用/禁用

- `enabled = true`：策略生效，会导出到 BFE；
- `enabled = false`：策略不导出；若已被 API-Key 或 Entity 引用，导出时该绑定也会跳过。

## 6. 导出到 BFE

### 6.1 入口

```go
func (m *RateLimitPolicyManager) RateLimitPolicyGenerator(ctx context.Context) (*iversion_control.ExportData, error)
```

### 6.2 导出流程

```
1. 查询所有 API-Key
2. 查询所有 RateLimitPolicy
3. 对每个 API-Key：
   a. 收集 API-Key 自身 policy_id
   b. 递归收集 Entity 层级向上的 policy_id
   c. 跳过 enabled=false 的策略
   d. 为每个启用的 policy_id 生成绑定关系
4. 将所有启用的策略写入 rate_limit_policies.json
5. 将所有绑定写入 api_key_rl_policy_bindings.json
```

### 6.3 Entity 层级递归

```go
func (m *RateLimitPolicyManager) fetchEntityRateLimitPolicyIDs(ctx context.Context, entity *EntityParam) ([]int64, error) {
    policyIDs := make([]int64, 0)
    if entity.RateLimitPolicyID != nil {
        policyIDs = append(policyIDs, *entity.RateLimitPolicyID)
    }
    if entity.ParentID != nil && *entity.ParentID != "" {
        parent, err := m.entityStorager.FetchEntity(ctx, &EntityFilter{EntityID: entity.ParentID})
        if parent != nil {
            parentPolicyIDs, _ := m.fetchEntityRateLimitPolicyIDs(ctx, parent)
            policyIDs = append(policyIDs, parentPolicyIDs...)
        }
    }
    return policyIDs, nil
}
```

### 6.4 绑定生成

```go
for _, policyID := range policyIDs {
    policy, exists := allPolicies[policyID]
    if !exists || policy.Enabled == nil || !*policy.Enabled {
        continue // 跳过未启用或已删除的策略
    }
    binding := APIKeyRateLimitPolicyBinding{
        Apikey: apiKeyValue,
        Policy: fmt.Sprintf("rlp-%d", policyID),
    }
    bindings = append(bindings, binding)
}
```

只有 `enabled=true` 的策略才会被写入 `rate_limit_policies.json` 并生成绑定；导出结构中的 `Enabled` 字段固定为 `true`。

### 6.5 策略命名

导出的策略名称统一格式为 `rlp-<policy_id>`，避免命名冲突并便于 BFE 索引。

### 6.6 规则 Redis Key 生成

控制面在导出时为每条 TPM/RPM 规则生成稳定的 Redis Key，并随配置下发给 BFE：

```go
for _, tpm := range policy.TpmConfigs {
    exportPolicy.Rules.TPM = append(exportPolicy.Rules.TPM, BfeTPMConfig{
        Name:          tpm.Name,
        Models:        models,
        WindowMinutes: tpm.WindowMinutes,
        MaxTokens:     tpm.MaxTokens,
        StepMinutes:   tpm.StepMinutes,
        RedisKey:      fmt.Sprintf("RL_TPM_rlp-%d_%s", policyID, tpm.Name),
    })
}

for _, rpm := range policy.RpmConfigs {
    exportPolicy.Rules.RPM = append(exportPolicy.Rules.RPM, BfeRPMConfig{
        Name:          rpm.Name,
        Models:        models,
        WindowMinutes: rpm.WindowMinutes,
        MaxRequests:   rpm.MaxRequests,
        Burst:         rpm.Burst,
        RedisKey:      fmt.Sprintf("RL_RPM_rlp-%d_%s", policyID, rpm.Name),
    })
}
```

**语义**

- Key 基于 `(policy_id, 规则 name)` 生成；
- `name` 在同一 `RateLimitPolicy` 内唯一，作为规则的稳定标识参与 Key 生成；
- 不提供单独"改名"语义：更新时若提交的 `name` 与既有规则不一致，视为删除旧规则 + 新增新规则——旧规则 Redis Key 被清理，新规则从零计数；修改 `model` 不改变 Redis Key，因此不会重置计数器；
- 删除规则会清理该规则对应的 Redis Key；新增规则会生成新的 Redis Key。
- 策略配置 `batch_limits` 时导出 `rules.batch` 段：仅 `max_create_rpm>0` 时生成计数 Redis Key（`RL_BATCH_rlp-<id>_rpm`，`model/shared.BuildBatchRateLimitRedisKey`）；`max_active_batches` 复用数据面共享 `BATCH_ACTIVE` ZSET 基数校验；文件字节/行数与 `mod_ai_batch.data` 全局硬顶取最小值作为生效值。

BFE 侧优先使用配置中的 `redis_key` 构建 Redis Key；对旧配置（无 `redis_key`）保留按规则名兜底的兼容逻辑，避免升级时计数器全部丢失。

### 6.7 导出文件

| 文件名 | 内容 |
|--------|------|
| `rate_limit_policies.json` | 所有启用状态的限流策略 |
| `api_key_rl_policy_bindings.json` | API-Key 到策略的绑定关系 |

## 7. BFE 侧预期行为

BFE 收到配置后：

1. 根据 `api_key_rl_policy_bindings.json` 找到 API-Key 对应的策略列表；
2. 请求到达时，按模型匹配 `rules.tpm` / `rules.rpm` 中的规则：
   - 优先匹配具体模型名；
   - 未命中时使用 `*` 默认限制；
3. 命中规则后，使用规则中的 `redis_key` 构建 Redis 计数器 key 进行限流检查；
4. 同时检查 `max_concurrency`；
5. 任一限制超出时返回 429 Too Many Requests。
6. 批量操作（`/v1/files`、`/v1/batches`，按操作类型分类）按 `rules.batch` 段检查批量创建 RPM、活跃 batch 数、文件字节/行数硬顶，超限返回 429；未绑定任何限流策略的 API-Key 同样受 `mod_ai_batch.data` 全局硬顶约束。

> BFE 具体计数器实现（Redis / 本地内存 / 滑动窗口）不在本文档范围。

## 8. 边界情况

| 场景 | 行为 |
|------|------|
| API-Key 与 Entity 都未绑定策略 | 不生成绑定，BFE 对该 Key 不限流 |
| 策略被禁用 | 不导出策略，也不生成绑定 |
| 策略被删除但仍有引用 | 导出时跳过该策略 ID，引用方不受影响（视为未绑定该策略） |
| 同一策略在层级中多次出现 | 生成多条绑定记录；BFE 去重或按命中顺序处理 |
| `max_concurrency = 0` | 取决于 BFE 语义：可能表示禁止并发或无限并发，需与 BFE 对齐 |
| `tpm_configs` / `rpm_configs` 为空 | 仅限制并发数 |
| 修改规则名 | 无单独改名语义；请求体中 `name` 与数据库不一致时，视为删除旧规则 + 新增新规则：旧规则 Key 被清理，新规则新 Key 从零计数 |
| 修改 model | 计数器不重置，因为 Redis Key 基于 `(policy_id, rule_name)` |
| 删除规则 | 该规则对应的 Redis Key 被清理 |
| 新增规则 | 生成新的 Redis Key |

## 9. 设计建议

1. **策略命名可配置**：当前强制 `rlp-<id>`，建议允许用户自定义导出名称或别名。
2. **去重绑定**：Entity 层级中若同一策略出现多次，导出时可去重以减少 BFE 配置量。
3. **限流与配额顺序**：建议在 BFE 中先校验限流、再校验配额，避免配额被无效请求消耗。
4. **限流超限提示**：返回 429 时可在响应头中增加 `Retry-After`，提升客户端体验。
